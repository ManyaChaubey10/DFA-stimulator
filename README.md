# DFA Studio

A React + Vite workbench for translating regular expressions into complete deterministic finite automata and exploring them interactively.

The **DFA Simulator** lets a student enter a supported language question, specify an alphabet, construct their own DFA in the diagram and synchronized transition table, simulate strings, save/load a machine, and check language equivalence. It does not fill in the student's answer. The **DFA Generator** constructs and minimizes a DFA automatically.

The app has a landing page at `/`, the automatic **DFA Generator** at `/generator`, and the student-built **DFA Simulator** at `/simulator`. The shared navigation keeps both tools mounted after first visit, so switching routes in one session preserves each tool's state. A student DFA can be downloaded as JSON and loaded again from a file.

## Project structure

- `frontend/` — React + Vite interface. Vite proxies API requests to FastAPI on `127.0.0.1:8000` during local development.
- `backend/app/automata.py` — regex parsing, Thompson NFA construction, subset determinization, and simulation.
- `backend/app/main.py` — FastAPI endpoints.

## Run locally (PowerShell)

Open two terminals at the repository root.

Terminal 1 (backend):

```powershell
backend\venv\Scripts\Activate.ps1
uvicorn app.main:app --app-dir backend --reload --host 127.0.0.1
```

If the virtual environment has not been created yet:

```powershell
python -m venv backend\venv
backend\venv\Scripts\Activate.ps1
pip install -r backend\requirements.txt
```

Terminal 2 (frontend):

```powershell
cd frontend
npm install
npm run dev -- --host 127.0.0.1
```

Open http://127.0.0.1:5173. FastAPI docs are at http://127.0.0.1:8000/docs and the health check is at http://127.0.0.1:8000/health.

For a separately hosted frontend, set `VITE_API_URL` to the FastAPI origin (for example `http://127.0.0.1:8000`) and restart Vite. The backend permits the local `localhost` and `127.0.0.1` Vite origins.

## Supported regular expression syntax

- Single-character literals from the declared alphabet, such as `0`, `1`, `a`, `b`.
- Concatenation: `01` or `ab`.
- Union: `0|1`.
- Kleene star: `a*`.
- One or more: `a+`.
- Optional: `a?`.
- Parentheses: `(0|1)*01`.
- Epsilon: `ε`; empty language: `∅`.

Input alphabet symbols are comma separated and must be unique single characters. Escaped operators and multi-character alphabet symbols are not part of this MVP.

The student editor currently uses comma-separated, single-character alphabet symbols. It supports adding, removing, and renaming states; choosing the start and accepting states; drawing transitions with the selected symbol; editing the transition table; dragging states; and undo/redo. Its simulator animates the submitted DFA and rejects incomplete transition functions. `POST /api/check` validates the student's machine and compares it with the reference language using product-automaton BFS; equivalent non-minimal machines are accepted, while an uninterpretable reference is reported as unavailable.

The diagram uses Dagre for layered positioning and React Flow for curved transitions, zoom, pan, fit-to-view, and a minimap for larger graphs. The app can switch between the generated and minimized DFAs; minimization uses reachable-state partition refinement.

## Natural language to DFA

Plain-English interpretation returns a small JSON AST, not code or transitions. The backend validates the AST against a closed operation schema and the declared alphabet. A separate compiler constructs complete atomic DFAs, combines Boolean constraints using reachable product construction, checks the transition function, and minimizes the result. Regex mode remains on its Thompson NFA and subset-construction pipeline.

The UI shows the interpreted AST and a plain-language summary with its source (deterministic or LLM). You can edit the AST JSON and compile that corrected interpretation. Invalid or ambiguous ASTs are rejected; transitions are always generated by the local compiler.

Supported AST operations:

- `starts_with`, `ends_with`, `contains`, `avoids` for literal patterns.
- `count_mod`, `count_exact`, `count_at_least`, `count_at_most` for a symbol count.
- `length_mod` for string length congruences/divisibility.
- `position_from_left`, `position_from_right` for a one-based position.
- `AND`, `OR`, `NOT` for Boolean language operations.
- `clarify` is an interpreter-only response that asks a question; it is never compiled into a DFA.

The credential-free deterministic interpreter recognizes common forms including “even number of 0s”, “exactly three 1s”, “second symbol from the right is 1”, “third symbol from the left is 0”, “length divisible by 3”, prefix/suffix/substring clauses, and conjunctions such as “starts with 0 and ends with 11” or “contains 101 but not 000”. It intentionally rejects mixed ungrouped `and`/`or` expressions and unclear wording. This grammar is not a general English parser.

### Optional LLM interpreter

When deterministic interpretation does not recognize the wording, the backend can query an OpenAI-compatible chat-completions endpoint. The model produces only schema-constrained AST JSON; the backend validates it and compiles it locally. No key is sent to or bundled into the frontend. Without credentials, deterministic descriptions continue to work and unsupported wording returns a configuration hint.

Configure in the backend process environment (for example, in a local untracked `.env` wrapper or your shell):

```powershell
$env:LLM_API_KEY = "your-key"
$env:LLM_PROVIDER = "openai-compatible"
$env:LLM_BASE_URL = "https://api.openai.com/v1"
$env:LLM_MODEL = "gpt-4o-mini"
uvicorn app.main:app --app-dir backend --reload --host 127.0.0.1
```

`LLM_API_KEY` may instead be named `OPENAI_API_KEY`. `LLM_BASE_URL` and `LLM_MODEL` can point to another compatible provider/model. Never place the key in a `VITE_*` variable. The interpretation endpoint is `POST /api/interpret`; `POST /api/dfa/natural` accepts `{ "alphabet": [...], "description": "...", "ast": {...} }` to compile an edited AST.

The compiler limits numeric counts to 200, modulo values to 50, right-relative position to 30, and construction size to 5,000 states. Alphabet symbols remain single characters. Arbitrary natural-language requests and non-regular languages are not supported; unsupported requests produce an error rather than an approximate automaton.

## Additional automata operations and language classification

`backend/app/automata.py` exposes reusable complete-DFA operations: `reachable_states`, `is_language_empty`, `complement_dfa`, and product constructions for union, intersection, difference, and symmetric difference. Product construction explores only reachable pairs; equivalence checking uses BFS and returns a shortest counterexample.

An explicit `{a^n b^n | n >= 0}` description (when both symbols are in the alphabet) is identified as a known non-regular language. The detector is intentionally narrow. Other unparsed, ambiguous, or unknown natural-language descriptions remain errors and are never automatically labeled non-regular.
